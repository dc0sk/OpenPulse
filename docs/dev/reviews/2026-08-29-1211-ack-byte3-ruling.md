# Review — the #1211 ruling that `AckFrame` byte 3 stays unenforced

Reviewer: Fable (adversarial). Date: 2026-08-29. Subject: the *recorded justification* for a
maintainer ruling, not the ruling itself.

## Prompt

The maintainer ruled (2026-08-28) that byte 3 of the 5-byte `AckFrame` stays **unenforced** when its
byte-0 presence flags are clear — contract *"must be zero on transmit, ignored on receive"* — after
#1165 enforced byte 0's reserved bits 7:5. PR #1215 writes that ruling into
`docs/dev/design/protocol-wire-spec.md` §5.1 with three supporting arguments and a falsifier.

The decision was explicitly **out of scope** for this review; the maintainer had already made it and
it was not to be re-litigated. What was submitted for falsification was the justification, because a
wrong reason in a wire spec is quoted back as fact for months. Specific asks:

- **A** — is argument 3 (CRC-8 robustness) numerically right, and is its *direction* even right,
  given that a frame reaching byte 3 has already passed the CRC?
- **B** — is argument 2's claim that an extension "must announce itself in byte 0 — there is
  nowhere else" actually true? Are there spare `AckType` codes, or other signalling channels?
- **C** — does `ack.rs` really allocate 3 + 5 bits with both flags settable at once?
- **D** — is the falsifier the right one, and can it ever fire?
- **E** — is there a TX-side gap the "ignored on receive" contract would hide forever?

The prompt asked for bluntness, for line references, and — if the justification held — for a ruling
on which reasons are load-bearing and which are decoration, on the grounds that decoration in a wire
spec is a liability.

## Verdict

**The ruling's outcome is defensible, but two of its stated reasons were wrong as written.** Both
have been corrected in §5.1 and in the mirrored entry in `release-1.0-criteria.md`.

**A — argument 3 was directionally backwards; CUT.** No corruption confined to byte 3 alone can pass
CRC-8 at all: an error polynomial of degree ≤ 7 cannot be a multiple of the degree-8 generator.
Independently re-verified here by enumerating all 256 byte-3 values over 200 random prefixes
(0 collisions) with a deliberately-weakened 4-bit CRC as the control (80 collisions — so the check
can fail). A CRC-passing corruption reaching byte 3 must also corrupt the CRC byte in a matched
pair; the review puts that slice at ~6e-8 of undetected patterns, and notes that almost all
CRC-passing corruptions also hit bytes 0–2, i.e. they decode to the *wrong* ACK today. Enforcement
would therefore mostly reject frames that are already semantically wrong — a benefit, not a cost.
The consequence chain the argument invoked is real and in fact understated (`transmit_arq` applies
`AckType::AckDown` unconditionally on a failed ACK decode), but a real cost on a vanishing slice
does not carry an argument. The reason is now recorded in §5.1 as *cut and why*, so it is not
re-argued from the issue thread.

**B — argument 2's premise was false; BROADENED.** Other announcement channels exist. Confirmed
directly: all eight `AckType` codes are assigned (`AckOk`=0b000 … `Abort`=0b111), so there is no
spare code point; and `SpeedLevel::from_u8` accepts only 1–20, so a set `recommended_level` of 0 or
21–31 is **rejected** by both decoders. Frame length is a third. The correct — and stronger —
statement is that *every* channel an extension could announce itself on is already fail-closed, and
byte 3 with its flags clear is the only one that is not. §5.1 now says that.

**C — argument 1 verified, with a caveat.** `b3 = (rec << 3) | rev` gives 3 + 5 bits, both settable
together and pinned by an existing test. The caveat: `new_with_reverse` has no production callers,
so every ACK shipped today leaves bits[2:0] free. "Fully allocated" is true of the *format*, not of
current traffic; §5.1 now says so explicitly.

**D — falsifier kept, with its standing price added.** It can only fire through a human reading
§5.1. Added to §5.1: because a third-party transmitter writing junk there is undetectable forever,
these bits can never be reclaimed without spending one of byte 0's seven remaining non-zero
patterns — and that scarcity is exactly what would tempt a future designer toward byte 3.

**E — two code-side gaps, deliberately NOT fixed in this docs PR.** (1) `ack.rs`'s module doc still
says only "backward-compatible: old receivers ignore this byte", which describes the pre-ruling
world and is where an extension author looks first; it needs a cross-reference to §5.1/#1211.
(2) The exhaustive encoder sweep checks byte 0 only, and no test pins byte 3's field bits to zero
when the corresponding flag is clear — including the `rec` set / `rev` clear shape that production
actually emits. Both are production-path changes needing the full gate, so they are filed as a
follow-up rather than bundled into a docs-only PR.

**Load-bearing vs decoration:** argument 2 (corrected) is load-bearing; argument 1 supports it;
argument 3 was decoration and is gone. The ruling stands on 1–2 alone.
