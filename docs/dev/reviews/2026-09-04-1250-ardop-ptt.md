# Review — #1250: the ARDOP TNC keys only its station ID

Reviewer: Fable (adversarial). Date: 2026-09-03. Reviewed **before implementation**. Verdict: *implement option A **plus** the async PTT edges unconditionally* — which is neither of the two options I offered, and the reasoning came from the reference implementations rather than from the code under review.

## Prompt

Carried the defect (issue #1250, filed and hand-verified: `assert_ptt` has two call sites, the station ID and the host's manual `PTT TRUE`, while all six traffic-carrying transmits go out unkeyed), the complication that `bridge.rs:419` records the split as deliberate ("worker-driven, unlike host-keyed data TX"), and three candidate designs — A: the TNC keys everything; B: honour the host-keyed model by emitting the async edges the TNC never sends; C: branch on `ptt_backend`. Seven questions were asked as falsification attempts: whether A breaks a real ARDOP host convention; lock ordering; where the guard belongs for `transmit_arq`, which transmits *and* listens inside one call; relay re-entrancy; whether the watchdog belongs in the same PR; what makes the gate non-vacuous; and the blast radius on KISS and the repeater.

## Verdict and the evidence behind it

**A + unconditional edges.** The reviewer checked two reference implementations rather than reasoning about the convention:

- **Pat's client (`la5nta/wl2k-go`, `transport/ardop/tnc.go`) never sends `PTT TRUE`.** It only *receives* the line, and `ArdopConfig.PTTControl` defaults off.
- **ardopcf (`pflarue/ardop`) keys its own hardware** (`-p` RTS, `-c` CAT, `-g` GPIO) **and still emits the edges** to the host, warning against both keying the same device.

So the convention is: the TNC always emits the edges; the TNC keys hardware if it has a device; the host keys its own rig only if separately configured. That makes C's branch on `ptt_backend` the wrong variable — the edges are protocol output owed to the host either way, not a substitute for keying — and B wrong on its face.

## Three corrections to my framing

1. `bridge.rs:419`'s "host-keyed data TX" describes a model **no real host implements**. It was never true, not merely unreached.
2. The `PTT TRUE` host *command* is **not ARDOP protocol at all** — absent from ardopcf's command list, never sent by Pat. It is an OpenPulse extension that `ptt_disconnect_safety.rs` depends on; keep it as a manual override, stop describing it as the data-TX keying mechanism.
3. **A leader delay exists in the reference and not here.** ardopcf waits after `PTT TRUE` before sending audio; our `transmit` starts playback immediately. So emitting the edges does **not** make host-only keying supported — it would clip ~50 ms of preamble, and #1049 measured that a truncated preamble does not demodulate. Documented as unsupported; the leader is split out.

## Design points that changed the implementation

**Lock order.** `SharedPtt`'s mutex is held only for one hardware call and `PttKeyGuard` holds no lock, so there is no deadlock hazard — but there is a **dead-carrier** hazard. `transmit_station_id` keyed *before* taking the engine lock, so contention left the rig keyed and silent for the wait. The correct order is engine lock first, then key: Rust drops in reverse declaration order, so PTT falls before the engine mutex is released. The station-ID site was reordered to match.

**`transmit_arq` must not be keyed across.** It transmits *and* listens for the ACK inside one call; keying across it holds the transmitter up through the listen. The daemon already solved this by not calling it (`ota_send_with_ptt` keys per attempt and releases before the listen). The bridge now runs the same loop over the engine's public pieces, so no PTT concept leaks into `ModemEngine`.

**Rejected: keying at the `stage_emit_output` seam.** Attractive because of this repo's "wire it at the seam" lesson, and wrong here — `transmit_ota_ack` emits a K=3 MFSK16 union with silence gaps under one keying, and the station ID emits digital + CW under one keying. A per-emit hook would key three times per union ACK. **Keying is a burst property, not a frame property, and the burst is defined by the caller.**

**Watchdog included, with a scope correction.** Without `spawn_watchdog` the deadline field is unused. But `release_ptt_on_disconnect` must not become an unconditional `unkey`: `unkey` releases the hardware *before* checking its armed state, which would break two existing controls. It is now gated on `is_keyed()` **and** a new `manual_keyed` flag — under A the worker's bursts are guard-released, so the disconnect handler exists only for the manual command, and a monitor client disconnecting must not cut a station ID mid-emission.

## What implementation then found, that the review did not predict

Adding the observer to the **manual** `PTT TRUE`/`PTT FALSE` command path made the TNC emit an async edge *and* a command response on the same stream, so a host reading the next line as its response read the event instead — caught by the existing `explicit_ptt_false_releases_once_and_disconnect_does_not_double_release` control. Corrected semantically rather than cosmetically: an edge exists to tell the host about keying it did **not** initiate, so the manual path passes no observer. Worker bursts and watchdog force-releases still emit.

## Gate requirements imposed

A spy-PTT fixture on the non-loopback bridge; a **positive control in the same test** (the station-ID path keyed before the fix, so asserting the spy sees it proves the spy is wired — without it the data assertion would pass vacuously against a spy connected to nothing); an assertion that PTT is **down** during the ACK listen; and — because a wrapper is only a guarantee if a bare call cannot silently return — a **source scan** requiring every `engine.transmit*` in `bridge.rs` to sit inside the helper, itself validated against a planted bare call so the scan cannot pass by matching nothing.

## Split out rather than folded in

1. A leader delay after `PTT TRUE`, without which host-keyed rigs clip the preamble.
2. `build_ptt` accepting `rts`/`dtr`/`cm108`/`gpio` — mixing it in makes the diff harder to check against the PR description.
3. KISS: `openpulse-radio` is a declared-but-unused dependency and `bridge.rs:98` claims "This TNC manages PTT … itself", the same false-comment archetype.
4. The repeater needs `SharedPtt` too, but its full-duplex hold is a *deliberate* long keying that the 180 s default would cut — a design decision of its own.
