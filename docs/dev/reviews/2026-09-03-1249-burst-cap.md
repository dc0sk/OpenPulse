# Review — #1249: sizing the RX burst cap for the rung the peer is sending

Reviewer: Fable (adversarial). Date: 2026-09-03. Reviewed **before implementation**. Verdict: *implement, but size from the OTA candidate set, not the profile* — the proposed design was overturned, and two consequences I had not identified were found.

## Prompt

Carried the defect (issue #1249, already filed and independently measured), my proposed design, and seven questions asked as falsification attempts rather than confirmations: whether the profile-max bound is so large it defeats the cap's purpose; whether `MAX_FEC_SLICE_FACTOR = 4` already over-provisions; whether `ota_active()` is the right predicate given `ota_lock_level` and the ARDOP legacy path; the interaction with #1254 (whether the DCD threshold that decides "carrier present" is even correct); whether the ACK path is touched; whether a simpler correct fix exists; and what would make the new gate non-vacuous given the existing one passes by asserting the wrong equality.

My proposal was:

```
cap = if ota_active() { max over profile.defined_levels() of burst_cap_samples(mode_for(level)) }
      else            { burst_cap_samples(rx_mode) }
```

## Verdict

**Overturned in favour of the OTA candidate set.** My premise — "the receiver cannot know which rung is arriving, so the only correct bound is the whole profile" — is half right, and the wrong half matters. The receiver cannot know which rung *is arriving*; it knows exactly which rungs it will *attempt*. `OtaRateController::rx_candidates()` returns at most two entries and `ota_decode_and_ack_inner` decodes **only** those plus the uncoded `fallback_mode` (which is `rx_mode`). A frame at any other rung is discarded regardless of how long the accumulator held it, so profile-max provisions buffer for frames the decode arm throws away by construction.

Adopted:

```
cap = max( burst_cap_samples(rx_mode),
           max over ota.rx_candidates() of burst_cap_samples(candidate mode) )
```

At `hpx_hf` session start the candidate set is `[Sl2]`, so nothing is lost at the entry rung; but the cap **narrows as the link climbs**, and because `ota_lock_level` and `ota_set_level_bounds` pin both candidate levels, a locked session gets a tighter cap for free — answering the `ota_lock_level` question without the new accessors profile-max would have needed.

## What it stopped me doing

`rx_mode` must not be set from the rung. That field also aims the receiver notch's protected band, where a wrong mode makes an interferer un-notchable — the same coupling the 2026-09-02 audit independently flagged. This ruled out the "just pass the rung as `mode`" fix that would otherwise look simplest.

It also rejected wiring keying-style logic at a shared seam here: the guard's value is not per-frame.

## The runaway-guard objection, answered by mechanism rather than by preference

My concern was that going from 37 s to ~298 s on `hpx_hf` weakens the backstop ~8×. The review reframed it: in the stuck-carrier regime a cap flush produces back-to-back slabs, and a frame inside a slab decodes only if it starts inside `burst_onset_scan_bounds`'s window (~0.5 s). P(decode) ≈ 0.5/37 → 0.5/298 — both effectively zero. **The guard has no recovery value; its function is memory bounding, and 9.5 MB still bounds.** A guard that "does not scale with the slowest rung" cannot exist if that rung must be received: the longest legitimate frame is the floor of any correct cap.

It declined to re-derive the cap from `fec_slice_factor` (×2 would suffice for the Rs rungs) on the grounds that coupling the cap to a per-attempt slice reserve is two constants agreeing by accident, and that inventing a third constant is worse than a documented over-provision that costs only where nothing decodes anyway.

## The measurement it demanded, and the result

It asked for one number before merging, because it could have changed the fix: the decode-pass wall time on a cap-length slab. Measured (release, `hpx_hf` at SL2, deterministic noise): **29.18 s / 30.84 s / 25.06 s** at 298 496 / 1 193 984 / 2 387 968 samples. **Flat** — bounded by the onset-scan window, not buffer length. The cap increase costs no decode time, so no companion change was needed.

The absolute figure is its own finding: ~25–31 s of `block_in_place` work on a slab that decodes nothing.

## Two consequences I had missed

1. **The defect keys the transmitter.** On a mid-frame flush the OTA arm decodes the first half, fails, and returns `Some(Nack)`; the daemon then keys PTT and transmits a NACK **while the peer is still sending the second half**. Three NACKs reach `nack_threshold` and collapse the ladder to SL1, which fits the cap — predicting an SL1↔SL2 oscillation on air. Inferred from code, not observed; recorded on the issue as such.
2. **A cap flush and a carrier-drop flush are different events and the engine conflates them.** By construction a capped burst is never one legitimate frame, yet both return as identical `Ok(Some(burst))`. Distinguishing them would let the daemon skip both the NACK and the expensive decode pass on capped bursts. Filed as #1255.

## Gate requirements imposed

The existing gate passes by asserting `cap(rung) > frame(rung)` — true, and not the property that matters. The review required: the production entry (`accumulate_capture`) in daemon-sized ticks rather than a function-level assertion; a **two-block** payload so the frame is the 131.8 s case; a **positive control in the same file** proving the cap still splits with no OTA session, so a later rise in `BURST_MIN_CAP_SAMPLES` fails the control instead of silently making the sibling vacuous; a narrowing assertion after `ota_lock_level`; and fixture amplitude above the DCD threshold so the verdict does not depend on the noise-floor tracker warming (#1254).

## Scope kept out

The multi-mode monitor decodes flushed bursts on its own engine at its own configured modes, so this fix does not cover "everything that could arrive" — stated in the PR rather than implied.
