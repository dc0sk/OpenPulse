# Review — the #1219 fix: CI lints judged PRs against a stale base

Reviewer: Fable (adversarial). Date: 2026-08-29. Subject: a design decision reviewed **before**
implementation, per the standing rule.

## Prompt

`traceability.yml` passed `${{ github.event.pull_request.base.sha }}` as the base to
`check-trailer.sh` and `check-review.sh`. PR #1214 (two `.odp` files) was classified DESIGN-CLASS
and failed `REVIEW-LINT` although its own diff touched no decision site. Two candidate fixes were
submitted for falsification — (a) resolve the base at runtime with `git merge-base`, (b) use the
checked-out merge ref's guarded first parent — together with a correction to my own filed diagnosis
and seven specific asks: whether (a) holds in both staleness regimes; whether `origin/<base.ref>`
is guaranteed to exist under `fetch-depth: 0`; whether (b)'s guard is sound or cleverness; **what
happens when base resolution fails**; whether `check-trailer.sh` has the same defect; whether a
third option was missed; and how to sabotage-verify a bug that needs a scheduling alignment I
cannot produce on demand.

The prompt asked for bluntness about anything wrong or unproven in the framing, explicitly
including the correction.

## Verdict

**The mechanism I filed was wrong twice; the fix is smaller than proposed; and the worst defect was
not the one I filed.** The review read the failing job's own logs — the authoritative source nobody
had opened — and settled it.

**Mechanism (both earlier accounts withdrawn).** `actions/checkout` fetches a *pinned* SHA
(`+2cd5c072…:refs/remotes/pull/1214/merge`), which is the payload's `github.sha`; the live
`refs/pull/N/merge` is never consulted, so its refresh schedule is a red herring. The inconsistency
is inside **one** payload: `github.sha` is minted per event (fresh even on `edited`) while
`pull_request.base.sha` was observed to refresh only on `synchronize`. Neither schedule is
documented — which is the design argument: **the fix must not take payload freshness as an input.**
Also withdrawn: "it flipped from passing to FAIL with no change to the PR". Review-lint had never
passed on #1214 (the earlier run died at the preceding trailer step on a dangling `CAP-7`), and the
triggering event was a body edit. What is true is that *the diffed files were unchanged while the
classification flipped*.

**Fix — (a), reduced.** Both scripts already compute the right thing from a branch ref
(`check-review.sh` diffs three-dot; `check-trailer.sh` walks `base..HEAD`), so the extra
`merge-base` step is redundant and hardcoding `origin/main` is wrong because a PR may target
another base. The change is two interpolated *arguments* → `origin/<base.ref>`, passed via `env:`
because a refname may legally contain `$`, `;`, `(`, `)`. `origin/<base.ref>` is guaranteed present:
the job's own fetch line is `+refs/heads/*:refs/remotes/origin/*` under `fetch-depth: 0`, and an
open PR's base branch cannot be deleted — a guarantee that would vanish under a shallow fetch, which
is why the guards below are mandatory rather than defensive.

**Candidate (b) rejected.** Its guard fails safe, but it buys nothing: wherever its first arm fires,
(a) computes an identical base, and it purchases that with `head.sha` — a payload field with the
same undocumented freshness that caused the bug.

**Rejected: checking out `head.sha`.** `trace.sh` and `reachability.sh` scan the *tree*, and today
they scan the merged state, so a PR that structurally conflicts with freshly-merged `main` is
caught. Checking out the head forfeits that and still needs a base ref for the diff.

**The worse defect — fail-open — confirmed and understated by me.** An unresolvable base did not
stop the job; it silently downgraded every PR to "ordinary change". Both scripts now exit 2. Three
shapes were measured passing beforehand, and the middle one is subtle: `git rev-parse --verify`
returns **0** for a well-formed 40-hex object *name* whether or not the object exists, so the
pre-existing existence check never fired on the most likely bad input — a stale SHA. `^{commit}` is
what actually checks. `check-trailer.sh` had the same shape by a different route (`rev-list` fails
into `2>/dev/null` → "no commits in range" → PASS).

**Sabotage-verification.** The new self-test cases were watched failing against the original
fail-open block before being trusted. One case is worth recording: weakening only the `^{commit}`
guard did **not** fail the self-test, because the later `git diff` guard catches that input too —
so the first sabotage was inconclusive and the block had to be reverted wholesale to produce a real
failure. A self-test that had shipped on the first, weaker sabotage would have been believed on
insufficient evidence.

**Historical replay, on the real inputs.** The failing run's merge commit `2cd5c072` was checked out
and the fixed classifier run against it: base `964faf55` (the stale value the job received) →
DESIGN-CLASS → FAIL; base `8e4f6d2c` (what the merge was actually built on, and what the fix
resolves to) → ordinary → PASS. Same tree, same message, only the base differs. Fable's trap was
observed: current `origin/main` must **not** be used for this replay, because #1214 has since merged
and there are now two merge bases; the historical SHAs are pinned instead.

**Carried, not fixed here:** `is_design_class` does not handle rename lines (`R100<TAB>old<TAB>new`,
so `$2` is the old path and a file renamed *into* `src/` is missed), and `docs.yml` has the same
`base.sha` pattern — it is `disabled_manually` (#1129), so it is recorded rather than changed.
