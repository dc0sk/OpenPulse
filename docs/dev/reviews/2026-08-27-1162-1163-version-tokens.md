# Adversarial review — version tokens for QSY and rendezvous (#1162, #1163)

**Reviewer:** Fable · **Date:** 2026-08-27 · **Covers:** two wire-format design decisions taken
together, reviewed BEFORE implementation.

## Prompt

Sent with both issues, the sibling conventions (`FILEXFER_VERSION`, `HINT_MAGIC`/`HINT_VERSION`),
and my verification that the rendezvous already emits a bare `OPHF` prefix in the same crate as
`hint.rs`'s `OPHF1`. Seven questions, the central one being an interaction created by earlier work
in the same session: #1193 registered `SigningDomain::QsyLine` with tag `OPQS` as a **prepended**
domain, so adding a *transmitted* magic to QSY lines forces a choice between reusing `OPQS` (tag
appears twice), converting the domain to in-band, or minting a new magic.

I flagged in advance that my inventory claim — "QSY and rendezvous are the last two on-air formats
without a version" — was exactly the shape I had got wrong three times already this session.

## Verdict

**It was wrong again.** `openpulse-freedv-auth`'s `AuthBeacon` transmits **bare canonical JSON with
no magic and no version** straight into FreeDV's codec2 data channel, is on-air, and was **absent
from the wire-break package table entirely**. Filed as #1206. (`AckFrame` also lacks one, but
deliberately — #1165 tracks it as reserved-bit headroom.)

**I also omitted the QSY RX site.** I gave the two daemon *encode* sites and missed `lib.rs:1355`,
where a UTF-8 payload that fails QSY decode **falls through to SAR routing** — and `sar_segment_id`
of arbitrary ASCII routes a non-zero first byte into **filexfer** reassembly. Survivable while QSY
was unrecognisable; with a magic it would mean a future-epoch QSY line silently feeding the file
assembler.

**Decision — convert `QsyLine` to in-band, firmly.** The `Prepended` placement existed *only*
because QSY lines had no fixed leading bytes, and #1162 removes that premise. The conversion is free
**now and only now**: the signed path has no production caller, so no signature changes meaning. Do
it in #1162 or it becomes a signing-domain break later. Reusing `OPQS` while staying prepended is
cryptographically harmless but structurally wrong — and registering `OPQS` in `RESERVED_MAGICS`, as
any transmitted magic should be, would make the registry's distinctness test panic on the duplicate.
Minting a third magic gives one context two permanent identifiers for nothing.

**Mechanics that must be right:** derive the transmitted prefix **by reference** from
`SigningDomain::QsyLine.tag()` — the registry's source scan sees only `b"…"` byte-string literals,
so an ASCII `"OPQS1"` literal would be invisible to it. The version drift-guard cannot live in core
(core cannot import `openpulse-qsy`), so the binding test belongs in the QSY crate. The in-band
`version()` is an ASCII **digit** here, not a raw byte — mirror the value and say so.

**Token shape:** `OPQS<version> ` as the first token — the only shape compatible with in-band
signing, since the magic must be the first signed bytes. Unknown version rejects with a **distinct**
variant, not `Malformed`.

**#1163:** adopt `OPHF1` exactly as `hint.rs` does, sharing `HINT_MAGIC`/`HINT_VERSION` **by
reference** so the dialect cannot fork into "OPHF1 hints / OPHF2 rendezvous". Airtime quantified
rather than asserted: the doc's example proposal is 111 bits → 118 with the version character, still
two JS8 data frames, with roughly one further candidate of headroom. Version mismatch → `None`,
matching the hint, because broadcast free text has nobody to send an error to.

**Two PRs, not one** — the package's own rule, and they share no code.

## Applied (this PR covers #1162 only)

All of it. `QsyLine` is in-band; the prefix and version both come from the registry by reference;
the unknown version reports itself; the daemon guard stops a QSY-identified line reaching
reassembly. #1206 filed. #1163 ships separately.

**Four tests failed on the format change and were right to** — they hardcoded the pre-#1162 wire
text. Rebuilt through the encoder rather than re-typed. A fifth, `token_too_long_rejected`, kept
**passing vacuously**: hand-built, it now rejected at the missing-token check without ever reaching
the length cap it is named for, and `Malformed(_)` matched both. It now asserts the message.

One process note against my own report: I called the suite green from a `head -8` of the results and
was wrong — four failures sat below the cut. Counted, the three affected crates are 764 passed,
0 failed.
