# Review — #1223: `trace.sh import` was destructive, and the fix is deletion

Reviewer: Fable (adversarial). Date: 2026-08-30. The maintainer had already ruled "delete import"; the
review was in flight and returned after the first commit, correcting three of my claims and naming a
damage channel the issue never mentioned. Recorded because the corrections matter more than the
verdict.

## Prompt

`do_import` rebuilt `requirements.yaml` from `docs/dev/requirements.md` + `traceability-matrix.md`
and documented itself as safe to re-run. Measured: `REQ-RX-02`, `REQ-RX-03`, `CAP-76`, `CAP-77`
appear zero times in either source, so a re-run deletes them; every construction site writes
`traceability: "baseline"`, resetting enforcement.

Three decisions were submitted for falsification — **D1** guard vs delete outright, **D2** whether
import should preserve `traceability` (breaking its "pure function of its sources" claim), **D3**
what a genuinely-new source id should get now that `baseline` is illegal for a non-grandfathered id
— plus: is the acceptance test discriminating, and *what is the safe way to exercise a command that
overwrites the file under test?*

## Verdict

**D1 = delete; D2 and D3 are moot.** The guard as specced covers **one of three** measured damage
channels; `--force` past it and the other two still happen silently. Making the guard complete would
mean refusing on any difference at all — "a deleted command with extra steps". The structural
argument is stronger than the empirical one: since the bright line (2026-08-09) edits land in the
yaml only, so the sources diverge **monotonically** — every future re-run is strictly more
destructive than today's. D2 is a false dilemma (a pure function of stale sources is a destruction
machine; a merge-preserving import is a different tool nobody asked for). Every D3 scenario
presupposes someone adding a requirement to the retired sources instead of the yaml, which is the
bright-line violation itself.

**Three corrections to my framing, all measured by running the importer sandboxed:**

1. **"11 NOT-GRANDFATHERED errors" is wrong — it is 7.** A *deleted* entry cannot carry a
   `traceability` field, so the four source-absent ids contribute none. And the failure arrives in
   waves: `do_check` short-circuits on vocabulary errors, so the first run after a re-import shows
   only those 7 and masks everything below.
2. **"The deletion is silent" is wrong for the two REQ ids.** `REQ-RX-02/03` have five in-code
   `// VERIFIES:` sites, and a binding naming an absent id hard-fails `DANGLING-BINDING`. Since
   enforcement *requires* bindings, an enforced requirement that vanishes is caught by construction
   — loud, though delayed behind the vocab wave.
3. **The genuinely silent damage is two channels the issue never named.** First, **`do_import` also
   rewrites `trace-orphan-baseline.txt`** — the allowlist `do_check` reads. A re-import *adds* the
   code of the vanished capabilities to it, so the deletions are not merely lost, they are
   **laundered**, together with any orphan accrued since the bright line. Nothing in `check` can
   notice, because the allowlist is the thing that was reset. Second, **surviving entries are
   corrupted, not just re-labelled**: the requirements-bullet regex is single-line, so
   `REQ-SEC-13`'s wrapped statement is truncated to its first line and its `covered_by` emptied;
   `REQ-QRM-01` and `CAP-01` mutate likewise. The importer is lossy even against ids present in its
   own sources.

**On exercising it safely** — the question that mattered, because the experiment's failure mode is
the defect. Module-import `trace.py` and repoint `YAML`/`ORPHAN_BASELINE` at a scratch directory.
One landmine: the final `print` calls `relative_to(ROOT)` and throws **after** both writes have
landed, so a naive harness sees a traceback and concludes "import failed, nothing written" when in
fact both files were fully written. Repoint `ROOT`/`REQ_MD`/`MATRIX_MD` at a temp tree instead.

**On the acceptance test I proposed** (four ids named → add one to the source → three named): it
does distinguish source-reading from a hardcoded list, but carries the corpus trap — `requirements.md`
is scanned only for `- **REQ-x** — text` bullets, so adding `CAP-76` there changes nothing and a
malformed bullet parses to nothing; either way the refusal still names four and reads as "the guard
ignores the sources" when the source was never actually altered. Assert that the added id **parsed**,
not just that the count moved. Moot under deletion, kept because it is the same
check-the-corpus-not-the-filter shape that has bitten twice.

## What shipped

`do_import` deleted, along with the helpers only it used (`REQ_MD`, `MATRIX_MD`, `_table_rows`,
`CAP_ID`, `PATH_RS`). `REQ_ID` stays (the binding scanner uses it) and `ORPHAN_BASELINE` stays (a
reader remains) — deleting import removes that file's only *writer*, which is the intended end
state: a baseline may shrink by hand and must never grow back by regeneration. Every surviving claim
that the command exists was swept, including `do_check`'s bootstrap message, which pointed a user
with a missing yaml at the destructive command as the recovery.
