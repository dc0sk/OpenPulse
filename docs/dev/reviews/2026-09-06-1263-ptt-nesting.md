# Review — #1263: SharedPtt has no nesting semantics

Reviewer: Fable, two passes. **The first proposal was rejected**; the second was accepted with three
named failure modes to close. Reviewed before implementation, per the standing rule.

## Consumer

Every production caller of the PTT surface, by `file:line` — the guard holders and, critically, the
**non-guard mutators** my first census omitted, which are precisely the paths any nesting rule must
cover:

| site | call |
|---|---|
| `ardop/bridge.rs:501` | `keyed()` — `keyed_transmit` |
| `daemon/lib.rs:1610` | `keyed()` — `keyed_transmit` |
| `kiss/bridge.rs:131` | `keyed()` — `keyed_transmit` (new in #1259) |
| `daemon/ptt.rs:73` | `keyed()` — the daemon's thin wrapper |
| `ardop/command.rs:294` | `key(None)` — the host's `PTT TRUE` |
| `ardop/command.rs:76`, `:314` | `unkey` |
| `daemon/server.rs:1602-1603` | `hw_assert` / `hw_release` |
| `daemon/lib.rs:2177/2181` | `arm` / `disarm` |
| CLI `transmit.rs:18`, `calibrate.rs:201`, `:328` | `assert_ptt` direct — off `SharedPtt` entirely |

**What this field bought:** the operator's manual key-down holds **no ownership token at all** — it
is `hw_assert` plus `arm`, never a guard — so any automatic guard's `Drop` releases it. That reframes
the issue from "nesting" to "one of the two holders was never represented".

## Prior art

In-repo sweep for a depth/ownership mechanism
(`grep -rn "depth\|refcount\|nesting\|reentran\|AlreadyKeyed\|owner"`): **nothing**.

That sweep was wrong. ARDOP already carries an ownership marker — `manual_keyed: AtomicBool`
(`bridge.rs:53`) — and it goes **stale**: a worker guard's `unkey` releases the host's key without
clearing the flag. I missed it because I grepped for the words I expected the mechanism to be called
rather than reading the struct. Third census error of the week, and the reason the field is worth
filling even when it comes back wrong: the omission is now written where the next reader sees it.

External: `chrissnell/omnimodem` (`references.md:314`) uses unkey-on-Drop RAII with an explicit
RX/TX interlock, and that file's *Revisit for* line already names it. **Unread** — a pointer, not
costed prior art.

## Twins

Four production `SharedPtt` holders — ARDOP (`bridge.rs:49`), daemon (`server.rs:591`), KISS
(`bridge.rs:60`), repeater (none yet, #1260, and it wants a deliberate full-duplex hold that the
180 s watchdog pushes against). A fifth releaser: the **independent watchdog thread**, which
force-releases without ownership *by design* — the safety property that constrains every option here.
Plus the three CLI paths that bypass `SharedPtt` altogether.

## Prompt

Two passes, both framed for falsification. The second opened: *"My first proposal was wrong in a way
that would have caused a §97.119 miss, so assume this one is wrong too and find where."*

## Verdict

### Pass 1 — rejected

1. **Wrong primitive.** I proposed that a nested `keyed()` refuse. `keyed()` is a thin wrapper over
   `key()`; the manual paths (`key(None)`, `hw_assert` + `arm`) never pass through it, so the rule
   would have left every path it was written for outside itself.
2. **It would have caused a §97.119 miss.** Verified in code, not taken on trust:
   `id_timer.mark_identified(now_ms)` is called *"Advance regardless of PTT success"*
   (`server.rs:1141`) and sets `last_id_ms = now` **and** `tx_since_id = false`
   (`station_id.rs:95-98`). A refused station ID would skip a full interval. My fix for a UX defect
   would have created a regulatory one.
3. The single-`select!` claim holds for the daemon and is **false for ARDOP**, whose `worker_loop` is
   an OS thread while `PTT TRUE/FALSE` run in `spawn_blocking` — manual-vs-automatic is a genuine
   race there.

### Pass 2 — accepted, with three failure modes to close

**The owner is the guard.** Not a thread id (ARDOP's assert and release run on *different*
`spawn_blocking` threads, so the operator could not release their own key; and the daemon's task
migrates across workers between awaits). Not a caller-supplied enum (a label any site can claim — v1's
hole in a new shape). Holding the live guard *is* ownership and the generation *is* the identity, so
"refuse a different owner" collapses to **"refuse any key while a live guard exists"**, and "the same
owner emitting under its own hold" means *emit without taking a second guard*. Consequence, accepted:
the non-guard API must go, at the five sites listed above.

- **F1, the worst — a stale owner defers the ID forever with the rig unkeyed.** If the watchdog
  clears `asserted_at` but leaves the owner behind, every later ID sees a foreign owner, returns
  `AlreadyKeyed`, correctly skips `mark_identified`, and defers indefinitely while nothing is keyed.
  Silent but for one log line per tick. The rule: *"already keyed" is `asserted_at.is_some()`, and
  every release path — `unkey`, the guard, the watchdog — clears the owner under the same lock.*
- **F2 — indefinite deferral by re-key inside one tick.** The ID lives in the 50 ms `rx_ticker` arm;
  `PttRelease`/`PttAssert` arrive on the same unbiased `select!`, so a client scripting
  `ptt-release; ptt-assert` inside 50 ms re-keys before the tick ever runs. Fix: **an ID that is due
  outranks a manual key at the acquisition point** — bounded by one ID's airtime rather than by
  operator behaviour.
- **F3 — "advance regardless" is load-bearing, so deferral must be scoped to `AlreadyKeyed` alone.**
  It exists to stop per-tick retry spam on a hardware fault. Under blanket deferral an `Assert` fault
  would hammer the rig's serial line at 20 Hz for 180 s and a `Transmit` fault would key/unkey at
  20 Hz — ~3 600 `PttChanged` pairs. So `Assert` and `Transmit` mark as today; only `AlreadyKeyed`
  defers. **This makes the third `KeyedTxError` variant mandatory, not optional** — overloading
  `Assert` puts the hardware-fault path onto the defer path.

**Item 6 as I wrote it trades a UI defect for a lost control point.** Today `ptt-release` drops the
hardware regardless of who keyed — the control operator's hard override. Making it a no-op leaves an
operator watching a runaway automatic burst for 180 s. Keep a force path: `PttRelease` when the live
holder is not manual force-releases, bumps the generation so the automatic guard's later drop is a
no-op, and warns. The panel defect is then a *panel* fix.

Also to close: a second `ptt-assert` while held must not re-arm (today `arm()` overwrites
`asserted_at`, so re-asserting every 170 s defeats the 180 s watchdog); a dead guard must not count
as a hold (`is_live()` = generation matches **and** `asserted_at.is_some()`); `AlreadyKeyed` must
surface as a `CommandError` for the CLI but still answer `PTT TRUE` for ARDOP hosts, which expect
idempotence.

## Scope

**Two PRs, both before #1260** — which is currently open and would otherwise be built on the
`key`/`unkey` surface PR-1 deletes.

- **PR-1** (`openpulse-radio` + the five migrated sites): the token, `is_live`, guards release only
  what they own, every release path clears the owner, watchdog stays blind. No refusal yet; the only
  behaviour change is that a stale guard no longer cuts a later key.
- **PR-2**: `AlreadyKeyed`, the three-way `KeyedTxError`, ID-outranks-manual, deferral state on both
  the daemon and ARDOP, the manual guard slots, `PttRelease` force semantics, and the panel.
